# FUSEBOX (Cenovus reuse workbench)

A reuse-first solution discovery and A/B workbench: a maintenance supervisor describes a problem in plain language, finds that a governed solution already exists, tries it on real sample data, and proves a proposed change side by side against the current product (real outputs, real diff, recorded human preference) before owner and IT decisions.

### IT-managed solution ZIPs

Package APIs require real Replit authentication. Demo personas and `?as=it` confer no upload/review rights. After the intended administrator signs in, inspect the `users` table and explicitly grant that verified account in the development database:

```sql
UPDATE users SET can_manage_solution_packages = true WHERE id = '<verified authenticated user id>';
```

Replace the placeholder with the exact verified ID; never grant all users. Revoke with the same targeted statement setting `false`. New users default to false, and no bootstrap auto-grants exist. Apply schema with `pnpm --filter @workspace/db run push` (also used by `scripts/post-merge.sh`). Production entitlement grants require a separately authorized database administrator.

`PRIVATE_OBJECT_DIR` must point to private App Storage. IT requests a ten-minute signed staging PUT URL, uploads a ZIP, then requests inspection. Limit: 20 MiB compressed, 60 MiB expanded, 5 MiB per file, 500 entries, 100:1 expansion. Inspection is static, serialized across server processes, and rejects unsafe paths, links, duplicates, encryption and nested archives. At most ten initialized uploads per account/hour and twenty mutations/minute. Invalid or failed inspections require a new upload. Successful originals are SHA-256 addressed with create-only generation preconditions; uploaded code is never executed. Signed-in users may list/download inspected packages; IT alone may upload/inspect/review. Only LIVE catalog solutions are eligible. Dependency extraction supports package.json and requirements*.txt declarations; other manifests remain available in the file inventory for manual review. Review confirms file/capability mappings only, never sandbox or integration validation. Staging uploads are private but may remain orphaned after failure/expiry; operators should configure lifecycle cleanup for the `solution-packages/staging/` prefix, never the immutable originals prefix.

## Architecture decisions

- Never fabricate an A/B advantage. Outputs are produced by actually executing both versions on the same input; the diff and the responsible steps come from the run traces; precision/recall appear only for inputs with labelled expected findings; summaries are computed only from recorded votes (blind votes and demo votes are labelled). The proposed version's production `performance` is `null` on purpose.
- The catalog is code, not data. Persisted: briefs, cases, decisions, runs, evaluations, test sessions, search events, and the governance overlay (`solution_versions`, `dispositions`).
- Governance overlay (`lib/governance.ts`): successor versions, folded capabilities with provenance, dispositions and preferred marks are persisted and merged onto every solution read through the catalog's resolver hook (held in memory, reloaded after each write, so `getSolution` stays synchronous). Owner approval (`approve_pilot` / `adopt_approach`) drafts the successor version on the parent (`Work Order Triage v3.3`) and seeds proposed dispositions (base retain+preferred; folded sources `fold_into`; everything else `retire`); Each version row also stores the approved production configuration (the experiment's Version B optional-module states and configurable values); once published, `Solution.production` carries the merged overrides and `productionCapabilities` / `defaultModuleStates` / `defaultConfigValues` read them, so the governed product and new experiments run exactly what was approved (e.g. Notifications "Immediate", a limited-evidence folded capability switched on). IT `approve_consolidation` publishes it (case status `folded`, `foldedInto` label, new current version, capability added to the parent, dispositions confirmed), `withdraw_consolidation` reverts both; a rejection withdraws the draft. Dispositions can be changed by IT (`PUT /cases/{id}/dispositions`) until confirmed; the label is computed server-side ("Proposed: …" until confirmed; a confirmed retire is "Retirement scheduled" until a migration note is recorded, never "retired"). Library and search rank confirmed-disposed products below the preferred one. Experiments compare against `parentVersion` via `getSolution(id, asOf)` so publishing never changes existing lineage; new cases branch from the new current version. Demo reset clears the overlay.
- A case doubles as a change proposal / A-B experiment: Version A = base solution production defaults, Version B = the case's moduleStates/configValues. Every new case starts with B equal to A (additions from other solutions off) so "Try this solution" shows the product as it is; the tray marks the recommended additions. The first `POST /cases/{id}/compare` moves a draft case to `tested`; any configuration change returns it to `draft` and marks older comparisons `staleB`.
- jsonb does not preserve key order: compare config objects by sorted entries, never by `JSON.stringify`.
- Blind sessions store pairs as `sampleInputId:runAId:runBId:left`; left/right is derived from the run id so it is stable but not guessable from order. Session responses are evaluations with `blind=true`.
- Decision flow: draft → tested → pilot_proposed (UI label "Proposed") → approved / changes_requested / deferred / rejected → folded (IT published it). Seeker proposes (`propose_pilot` = improvement to the parent; pilot exposure is a detail inside it; `propose_capability` only when a capability was added; `request_new_family` is the exception and needs a reason); owner approves/requests changes/rejects/defers; IT approves the consolidation direction only after the owner approved (`approved` → `folded`) and can withdraw it (`folded` → `approved`). A configuration edit after "changes requested" returns the case to `draft`. Folded and declined experiments stay visible on their group page (settled; no further group actions) but leave the My Solutions list and "in progress" counts. `promotionState` records which route was taken. Grouped owner decisions (`adopt_approach`, `merge_approaches`, `request_more_evidence`, `keep_local`, `decline`) go through `/my-solutions/{solutionId}/groups/{key}/decisions` and apply to every experiment in the group; adopting one keeps the others as local experiments.
- Experiments stay under the parent product: every case stores parent version, owner (name/team), intent, promotion state and a `demo` flag; `lineage` (added/removed/changed settings + fingerprint + derived intent) is recomputed from the stored configuration on every read, never persisted. Default title "Experimental improvement to <parent> v<version>". Grouping key = the normalized stated intent when the person wrote one, else the added capability id, else a slug of the first requirement; capability/identical-configuration matching is only a fallback when a side has no stated intent. Any configuration edit withdraws a proposal (status and `promotionState` both reset). Experiments are listed on their parent's Solution page ("Experiments in progress") and in My Solutions groups only — never in the library or search.
- AI is used only to interpret the pain point into the brief (cached for the demo prompt, 15s timeout, rule-based fallback). Editing Today/Better writes back into `painPoint`/`desiredOutcome` so matching follows the user's words. Editing Better re-derives the derived requirements (rule-based, instant) and keeps user-added ones.
- Reuse-fit scoring (`lib/reuse-check.ts`) is deterministic: problem fit 30 / input-output 20 / workflow position 15 / user context 10 / data-control 15 / maturity-evidence 10. Paths: ≥80 try existing, 60–79 start from and improve, <60 new experiment allowed; hard exclusions (cannot consume the base's output, control conflict, missing dependency, deprecated or unowned retirement candidate) override the score. Problem fit is DF-weighted over catalog words and needs ≥2 shared words; the other dimensions scale with relevance. Coverage: the best capability ≥60 decides — from the recommended product → covered, from a same-business-problem sibling → covered by a reusable capability, otherwise uncovered.
- IT Portfolio (`routes/overview.ts` `/portfolio`, `pages/portfolio.tsx`): four questions (reuse before build, capability acceptance, improvements folded, production variants per family) and two failure measures (duplicate effort after development, time to first useful test). Every metric carries its numerator/denominator, a plain definition and a demo-data flag; a metric with nothing to count reads "No data yet", never 0%. Reuse metrics come from `reuse_events` with a recorded choice: `use`/`improve` are written only when a capability is actually tried or improved (or a case is created from the check), `create` for a new approach or capability request, `dismissed` for "Not now"; opening a page records `explored`, which never counts, and hard-excluded options never count as reuse. Folding counts cases with a recorded proposal decision (seeker proposed or owner adopted), not terminal status; variants/duplicates from the catalog plus confirmed retirements (a product leaves production only when its migration note is recorded); time to first test = median case `createdAt` → first evaluation (the seed backdates demo cases/runs/votes so this is honest). The queue is exception-only (consolidation awaiting IT, products without owner/support, confirmed retirements without a migration note, new-family requests with the requester's reason), one primary action per row; the consolidation detail (`components/consolidation.tsx`) opens in place under the row and stays pinned after the decision until closed. `/portfolio?case=<id>` opens a consolidation record that is no longer in the queue (linked from a product's version history) so a published decision can still be withdrawn. Usage counts are context only.
- Portable modules: a capability may declare `portableTo` business problems (Safety Signals from Incident Commander → work-order triage). It appears in the tray of cases for those problems and is recommended only when a brief requirement calls for it; sibling-solution candidates and lineage are unchanged. A case created from a reuse check (`moduleIds`, `reuseEventId`) starts with that module on in Version B and records the path taken.

IT queue item only when ownerless or when a component duplicates a certified capability. ## Gotchas

- Run `pnpm run typecheck:libs` before `pnpm --filter @workspace/api-server run typecheck`.
- Restart the API workflow after backend edits (it runs a build, not a watcher).
- Running a TS script against api-server code: bundle with esbuild from `artifacts/api-server` (`npx esbuild scripts/x.ts --bundle --platform=node --format=esm --packages=external --outfile=/tmp/x.mjs`) and run with node; `scripts/safety-check.ts` and `scripts/reuse-check-try.ts` are examples (engine safety output; reuse-fit scores for sample needs).
- Orval: an operation with both path and query params generates `XxxParams` in both the types and zod outputs and the re-exports collide; avoid that combination (return a list instead and filter client-side).
- Browser journeys: Playwright scripts under `/tmp/pw` (chromium at `/repl/tools/bin/chromium`, base `http://localhost:80`, `?as=seeker` to pass the persona gate); the preview screenshot tool cannot pass the gate.
- Pilot plan thresholds and guardrails are derived from recorded evidence and the base solution's locked capabilities; keep catalog `controlType`/`category` accurate.
- Configuration fingerprints (`lib/fingerprint.ts`, `CATALOG_VERSION` in `data/catalog.ts`): every run stores `configFingerprint` (sorted capability ids@version + sorted settings + catalog version) and every vote stores `fingerprintA`/`fingerprintB`. Evidence (case evaluations, owner review, My Solutions totals, IT A/B-preference metric) counts only votes whose fingerprints equal the case's current baseline/Version B (`currentFingerprints`); the rest is reported as "set aside", never merged. `pairRejection` is the single rule for refusing a vote or expiring a blind pair (409). Bump `CATALOG_VERSION` when a capability's behaviour changes so old runs stop matching.
