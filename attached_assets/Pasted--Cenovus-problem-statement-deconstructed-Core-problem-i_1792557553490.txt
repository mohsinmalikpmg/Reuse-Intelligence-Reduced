# Cenovus problem statement, deconstructed

## Core problem in one sentence

**AI has made it easy for teams to create working solutions, but Cenovus lacks a repeatable way to discover overlapping work, compare it objectively, preserve the strongest capabilities, and converge on one governed product.**

The challenge is therefore not primarily:

> How do we help people build solutions faster?

It is:

> **How do we convert decentralized experimentation into reusable organizational capability without creating duplicate products and unsupported variation?**

---

# 1. Causal structure of the problem

The problem statement describes a clear chain:

### Trigger

AI-enabled development and rapid prototyping lower the effort required to create functioning solutions.

### Behaviour

Multiple teams or individuals independently solve the same or similar business problem.

### Positive consequence

Different teams produce useful ideas, workflows, features, and technical approaches.

### Negative consequence

The organization accumulates:

- Duplicate effort
- Parallel products
- Fragmented workflows
- Inconsistent functionality
- Multiple technical approaches
- Unclear product ownership
- Increasing support complexity

### Missing organizational capability

Cenovus does not have a repeatable way to:

- Recognize overlapping work
- Compare solutions fairly
- Determine which elements are strongest
- Combine useful elements
- Resolve conflicting approaches
- Establish one preferred product
- Retire redundant solutions

### Desired future state

A repeatable process that moves:

**Many independent solutions → one stronger, optimized, governed product**

The word **repeatable** is important. The required answer is not merely one consolidated application. It is a mechanism that can be applied whenever duplicate solutions emerge.

---

# 2. Pain points

Some pain points are explicitly stated in the problem. Others are implied by what would be necessary to solve it.

## A. Explicit pain points

### 1. Duplicate development effort

Several teams can independently invest time in solving essentially the same problem.

Consequences include:

- Repeated design and development effort
- Repeated approvals
- Repeated testing
- Repeated maintenance
- Opportunity cost from teams not working on distinct problems

### 2. Fragmented solutions

Functionality becomes distributed across multiple applications or prototypes.

One solution may have the best interface, another the strongest workflow, and another the best analysis capability. No single product contains the complete value.

### 3. No consistent method for comparison

Parallel products may use different:

- Workflows
- Inputs
- Outputs
- Features
- Data
- AI models
- Technical architectures
- Evaluation approaches

Without a common comparison method, decisions become driven by presentation quality, team influence, familiarity, or opinion.

### 4. No mechanism to reconcile or merge solutions

Even when teams recognize duplication, there is no simple way to decide:

- Which product should become the base
- Which capabilities should be preserved
- Which implementations should be rebuilt
- Which differences are legitimate
- Which differences are accidental
- Which products should be retired

### 5. Valuable experimentation is not converted into shared value

Decentralized experimentation creates useful innovation, but the resulting knowledge remains attached to individual solutions rather than becoming reusable organizational capability.

The organization receives the cost of experimentation without consistently capturing its full benefit.

---

## B. Implied pain points

These are not written directly on the slide, but a workable response must address them.

### 6. Teams may not know what already exists

Duplicate work often begins before development because existing solutions are difficult to discover.

This produces a critical failure:

> The organization recognizes duplication after effort has already been spent.

The product must therefore prevent duplicate starts, not only consolidate completed work.

### 7. Business problems are described inconsistently

Two teams may describe the same need using different language.

For example:

- “Maintenance note analysis”
- “Recurring equipment issue detection”
- “Work-order intelligence”
- “Failure-pattern identification”

A name-based catalogue will not reliably detect this overlap.

### 8. There is no shared definition of “better”

A solution may be:

- Easier to use
- More accurate
- Cheaper
- Better governed
- More technically maintainable
- Better integrated
- More configurable

These strengths may conflict. The organization needs an explicit decision framework rather than a vague “best solution” label.

### 9. Feature lists do not prove business value

Knowing that one solution has “clustering” and another has “action tracking” does not show what changes for the user.

Users need to see:

- The same input
- The different workflows
- The resulting outputs
- Which workflow element caused the difference

### 10. Experimentation can itself create sprawl

If every user-created modification becomes another published workflow, the consolidation platform recreates the original problem internally.

The system must distinguish:

- Experiment
- Local configuration
- Approved configuration
- Shared capability
- Product version
- New solution

### 11. Successful experiments may not be folded back into the core product

A useful improvement can remain an isolated branch unless there is a lifecycle for:

- Proposal
- Testing
- Owner review
- Promotion
- Integration
- Versioning
- Publication
- Retirement of superseded alternatives

### 12. Consolidation may stop before decommissioning

Creating a new consolidated product does not eliminate fragmentation if all previous products remain active.

Consolidation must include migration and retirement.

### 13. Ownership and incentives may be unclear

Solution creators may resist consolidation if it appears to:

- Eliminate their work
- Remove ownership
- Ignore their contribution
- Add support obligations
- Force changes onto existing users

The process must preserve provenance and recognize contributions.

---

# 3. User-facing pain versus underlying requirements

Strategically, **pain and requirement are different concepts**:

- A pain describes what is wrong today.
- A requirement describes what the future solution must do.

However, users should not have to classify their thoughts into formal categories.

The interface should continue using:

### Today

What is happening now?

> “Supervisors manually review work-order notes and sometimes miss recurring equipment problems.”

### Better

What outcome is needed?

> “Identify recurring problems quickly and consistently using existing work-order information.”

The application can internally derive:

- User
- Pain points
- Functional requirements
- Constraints
- Data requirements
- Controls
- Success measures

This preserves analytical rigor without making the user complete a requirements document.

---

# 4. Requirements for the solution

The requirements fall into six capability groups.

## A. Prevent unnecessary duplicate effort

The platform must identify existing work before a user begins building.

Required functions:

- Plain-language problem intake
- Semantic and metadata-based search
- Similar business-problem detection
- Existing solution recommendations
- Existing capability recommendations
- Similar experiment detection
- Contextual reuse prompts when a requirement or step is added

This check should occur when the user:

- Describes a problem
- Adds a requirement
- Adds a workflow step
- Describes a new capability
- Saves an experiment
- Requests publication

The system should offer three paths:

1. **Reuse existing**
2. **Improve existing**
3. **Create a genuinely different experiment**

It should not automatically block new ideas.

---

## B. Make independently created solutions comparable

Every solution needs to be represented through a common structure.

Minimum normalized description:

- Business problem
- Intended users
- Desired outcome
- Workflow
- Capabilities
- Inputs
- Outputs
- Data sources
- Integrations
- Controls
- Dependencies
- Owner
- Support status
- Evidence
- Known limitations

Solutions should be decomposed into capabilities rather than compared only as whole applications.

This allows the platform to identify that:

- Solution A has the strongest production workflow.
- Solution B has the strongest pattern-detection capability.
- Solution C has the strongest follow-up process.

---

## C. Evaluate alternatives with evidence

The platform needs a deterministic and explainable comparison framework.

At minimum, it should evaluate:

- Business-problem fit
- Desired-outcome fit
- Workflow coverage
- User fit
- Production readiness
- Evidence maturity
- Data and integration fit
- Control compatibility
- Maintainability
- Change effort

The user must be able to select:

**Why this solution?**

and see the principal reasons behind the recommendation.

The platform should distinguish:

- Measured evidence
- User feedback
- Production usage
- Simulated data
- AI recommendation
- Unsupported claim

---

## D. Show the functional consequence of differences

The strongest differentiator remains an interactive A/B workbench.

Requirements:

- Version A and Version B use the same input.
- Version A represents the existing governed product.
- Version B contains the proposed change.
- Users can add, remove, enable, disable, or configure eligible capabilities.
- Both workflows execute.
- Both produce actual outputs.
- Differences are highlighted.
- Differences are attributable to workflow steps.
- Users can select which output is more useful.
- Results remain connected to the exact workflow version tested.

This is more useful than a static feature comparison because it lets users understand what each difference actually changes.

---

## E. Convert experiments into governed improvements

The application must treat experimentation as a branch of a parent product, not as the automatic creation of another solution.

Required lifecycle:

1. Experiment
2. Test
3. Compare
4. Propose
5. Review
6. Promote, merge, retain locally, or reject
7. Update the parent product
8. Publish the governed version
9. Retire superseded products or branches

Every experiment should retain:

- Parent solution
- Parent version
- Exact modification
- Capability provenance
- Test inputs
- Outputs
- Evaluations
- Owner
- Status
- Similarity to other experiments

A user-created experiment should remain hidden from ordinary Library users until it becomes an approved configuration or reusable capability.

---

## F. Govern the product portfolio

The platform must help business and IT owners answer:

- Which business problems have multiple active products?
- Which products are preferred?
- Which capabilities are duplicated?
- Which experiments are converging on the same improvement?
- Which changes have evidence?
- Which products can be folded or retired?
- Are supported configurations increasing or decreasing?
- Are users finding existing capabilities before building?

IT should receive a prioritized decision queue, not an exhaustive catalogue of every user action.

---

# 5. Non-functional requirements

These determine whether the platform is usable and credible.

## Simplicity

The user should see:

- One decision
- One recommendation
- One primary action

Supporting evidence should be available on demand.

## Explainability

Every recommendation must show:

- Why it matched
- What requirement it addresses
- Where it came from
- What evidence supports it
- What constraints affected the decision

## Trustworthiness

The system must not present:

- Predictions as observed results
- Simulated users as real users
- Longer outputs as more accurate
- One vote as conclusive evidence
- Proposed retirement as completed retirement

## Reversibility

Users must be able to:

- Undo workflow changes
- Restore the baseline
- Rerun tests
- Reject a proposal
- Roll back a pilot
- Preserve previous versions

## Governance without friction

Experimentation should remain accessible. Governance should become strict only when a user seeks to create:

- A supported configuration
- A shared capability
- A production version
- A new solution family

## Interoperability

The model must be able to describe solutions created in different technologies rather than assuming every solution uses the same application framework.

---

# 6. Outcomes of success

Success needs to be measured at several stages.

## A. User outcomes

### Solution seeker

- Finds a relevant existing product quickly.
- Understands why it is relevant.
- Can try it using a real input.
- Can identify what is missing.
- Can improve it without starting over.

### Existing solution owner

- Sees exactly what is proposed.
- Understands which users and outputs are affected.
- Reviews evidence before approving change.
- Can adopt improvements without losing product control.
- Receives related proposals as one grouped improvement rather than many separate requests.

### IT or business technology owner

- Sees duplicate effort before it becomes another production product.
- Understands which product should be the base.
- Can trace capability provenance.
- Sees evidence supporting consolidation.
- Can complete migration and retirement decisions.

---

## B. Product outcomes

A successful product should demonstrate that it can:

- Detect overlapping solutions.
- Recommend the strongest base product.
- Identify useful capabilities from alternatives.
- Execute current and proposed workflows.
- Show actual output differences.
- Capture user preference.
- Fold approved improvements into the parent product.
- Update the Library.
- Move redundant products toward retirement.

---

## C. Portfolio outcomes

The organizational portfolio should show:

- Fewer independent solutions per business problem
- Fewer unsupported applications
- Greater reuse of shared capabilities
- Fewer duplicate development starts
- Fewer approved configuration variants
- Faster movement from need to useful solution
- More experiments folded into existing products
- More completed retirements
- Clear ownership for supported products and capabilities

---

## D. Business outcomes

Ultimately, consolidation is only valuable if the resulting product improves work.

Relevant measures include:

- Task completion time
- Quality or accuracy
- Error rate
- User effort
- Adoption
- Reliability
- Control compliance
- Support cost
- Operating cost
- Time to implement improvements

These measures will vary by business problem. The platform should not pretend that one universal metric applies to every solution.

---

# 7. Recommended metric hierarchy

## North-star outcome

> **Percentage of business needs resolved by reusing or improving an existing governed solution without creating another standalone production product.**

This directly reflects the problem statement.

## Leading indicators

These show whether the platform is preventing waste:

- Percentage of problem submissions with a relevant existing match
- Percentage of users who try an existing solution before creating
- Percentage of added requirements matched to an existing capability
- Percentage of proposed new steps redirected to reuse or improvement
- Time from problem description to first useful test
- Duplicate development attempts detected before work begins

## Improvement indicators

These show whether experimentation is producing value:

- A/B tests completed on actual outputs
- Percentage of proposed changes preferred over the baseline
- Percentage of changes with current-revision evidence
- Percentage of experiments joined or merged with similar work
- Percentage of successful experiments proposed to parent-product owners

## Consolidation indicators

These show whether the organization is actually moving from many to one:

- Active standalone solutions per business problem
- Approved configurations per solution family
- Capabilities reused across products
- Products marked for retirement
- Products actually retired
- Improvements folded into parent products
- Duplicate products created after platform adoption

## Failure measures

These are particularly important:

- Duplicate effort identified only after development
- Experiments that become unsupported production variants
- Approved consolidations where source products remain active
- Recommendations without evidence
- Configurations without owners
- Capabilities without support or provenance

---

# 8. Traceability matrix

This is the most useful structure for anchoring product decisions.

| Pain point | Required product behaviour | Evidence of success |
|---|---|---|
| Teams build before knowing what exists | Search automatically when intent is expressed | Existing solution offered before development begins |
| Solutions use different descriptions | Normalize problems, workflows, capabilities, inputs, and outputs | Comparable solution profiles |
| Strong capabilities are scattered | Decompose products into reusable capabilities | Capability from one product can improve another |
| There is no objective comparison | Run the same input through A and B | Actual output difference and user evaluation |
| Similar experiments create new sprawl | Store experiments beneath a parent solution and detect similarity | Similar changes are joined, reused, or merged |
| Successful ideas remain isolated | Promote evidence-backed capabilities into the parent product | Library shows an improved governed version |
| Consolidation stops at recommendation | Record dispositions, migration, and retirement | Source products are folded or retired |
| Users are overwhelmed by technical detail | Recommendation-first interface with detail on demand | First-time users complete the journey without instruction |
| IT receives too much low-value information | Present exception-based decision queue | IT sees only decisions requiring intervention |
| Recommendations appear arbitrary | Show deterministic scoring and constraints | User can answer “why was this selected?” |

Every significant feature should map to at least one row in this table.

A feature that does not materially reduce a pain point or improve a success measure should be deprioritized.

# 9. Design philosophy derived from the problem

## 1. Reuse before build

The platform should search organizational knowledge before allowing development effort to begin.

## 2. Recommendation before configuration

Users should start with the best existing product, not a blank canvas.

## 3. Experiment is not product

A modification remains an experimental branch until evidence, ownership, and governance justify promotion.

## 4. One preferred solution family per business problem

There may be approved configurations and shared capabilities, but ordinary users should not have to choose among dozens of near-identical products.

## 5. Compare outputs, not just feature lists

Functional output differences are easier for users to understand and provide stronger evidence than architecture or feature matrices.

## 6. Preserve ideas without preserving every implementation

A valuable capability may be rebuilt inside the governed product rather than reusing its original code.

## 7. Evidence before promotion

Users can experiment freely. Supported production variation requires evidence and ownership.

## 8. Variation must earn its existence

A separate approved configuration should exist only where a legitimate difference in user, process, control, data, or operating context requires it.

## 9. Governance should occur at the transition to support

IT should not approve every experiment. It should govern what becomes supported, shared, or production-grade.

## 10. Consolidation is not complete until retirement

A recommendation or replacement product is insufficient while redundant products remain active.

## 11. Provenance must be preserved

Every retained capability should show its source, owner, evidence, and change history.

## 12. Simplicity is a control mechanism

A clear preferred path reduces both user confusion and unnecessary product variation.

---

# 10. Explicit non-goals

The problem statement does not require:

- A general-purpose AI application builder
- A marketplace containing every prototype
- Unlimited production configuration
- Automatic code merging
- Automatic retirement decisions
- A large portfolio dashboard
- Synthetic predictions presented as proof
- A complex development environment for ordinary business users

Those capabilities may be interesting, but they can distract from the actual challenge.

---

# 11. Minimum complete solution for the hackathon

A complete response to the problem statement should prove this sequence:

1. A user describes a business problem.
2. The platform identifies existing overlapping solutions before new development begins.
3. It explains which existing solution is the strongest production base.
4. It identifies useful capabilities from the alternatives.
5. The user adds one capability to a proposed version.
6. A and B execute against the same input.
7. The user sees how the output changes and which capability caused it.
8. The improvement is saved under the existing product, not as another standalone solution.
9. The owner reviews the evidence.
10. IT approves the many-to-one consolidation direction.
11. The Library updates to show the governed successor.
12. Redundant products receive explicit folding or retirement statuses.

That demonstration would prove all four major elements of the Cenovus challenge:

- Discovery
- Comparison
- Consolidation
- Repeatability

# Strategic anchor

The strategy can be summarized as:

> **Prevent duplicate effort before it begins, prove improvements through actual output comparison, and channel successful innovation back into one governed product.**

The corresponding product philosophy is:

> **Find before building. Test before promoting. Consolidate before publishing. Retire what is replaced.**
