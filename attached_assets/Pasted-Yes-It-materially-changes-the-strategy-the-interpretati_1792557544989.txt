Yes. It materially changes the strategy, the interpretation of the current app, and the order of development work.

The earlier strategy was still too focused on **managing duplication after users had started customizing or creating**. The improved strategy is to **intercept duplicate effort at the moment intent is expressed**, while still allowing a user to challenge or improve what already exists.

The governing question changes from:

> How do we govern and consolidate user-created variations?

to:

> How do we help users reuse organizational knowledge before they expend development effort, while still giving them a controlled way to prove that a new approach is better?

The A/B workbench remains the product’s primary differentiator. Its role changes slightly: it is no longer mainly a place to invent alternatives. It becomes the place where users **try an existing capability, improve it, or challenge it with evidence**.

# 1. Strategy change

## Earlier model

**Discover → Customize or create → Test → Detect duplication → Govern**

The problem with this sequence is that duplicate prevention occurs too late.

## Revised model

**Express intent → Check what already exists → Try the closest match → Improve or challenge it if needed → Test actual outputs → Propose the improvement to the parent product → Govern only what becomes supported**

This changes several design principles.

| Earlier position | Revised position |
|---|---|
| Experiment freely, then detect similar work | Search continuously before and during experimentation |
| New capability creation is a primary path | Reuse and extension are primary; new creation is an explicit third path |
| IT reviews duplicate configurations after creation | The product prevents most duplicate starts; IT handles exceptions and production promotion |
| The workbench begins with available modules or a blank addition | The workbench begins with a relevant existing capability whenever one exists |
| Similar experiments are grouped after saving | Similar experiments are surfaced before the user spends effort |
| The Library is an important supporting feature | The Library is the knowledge foundation of every creation interaction |
| A/B proves whether a newly created feature works | A/B proves whether an existing, modified, or genuinely new capability improves the output |
| Usage statistics identify popular variants | Metrics show whether reuse happened before build and whether successful improvements were folded into existing products |

# 2. How this changes the current-state assessment

The application did not become worse. The evaluation standard became more precise.

The previous approximate score of **71/100** evaluated Fusebox mainly as a consolidation, experimentation, and governance product.

Under the revised framing, the current source state would score approximately **66/100**. This is not because capability was lost. It is because **proactive duplicate-effort prevention now carries more weight**, and the application currently performs most similarity and consolidation reasoning after a case or modification has already been created.

## Current strengths that become more important

### Library and search

The existing Library, global search, problem grouping, solution cards, and capability relationships should now be treated as core infrastructure rather than supporting pages.

They already provide much of what is needed for proactive reuse.

### Pain-point interpretation

The `Today → Better` model is well suited to early matching. It is easier for a business user than asking them to define detailed technical requirements.

### Actual A/B execution

The same-input, actual-output A/B workbench remains the strongest feature. It provides a defensible way to determine whether:

- The existing capability is sufficient.
- A modification is genuinely useful.
- A competing approach performs better.
- A proposed improvement should be incorporated into the parent product.

### Capability provenance

The existing ability to retain where capabilities came from becomes central. It allows a user to improve an existing product without creating another independent solution.

## Shortcomings that become more significant

### The creation flow still begins too easily

A user can create a case, add modules, or create a branch without first receiving a strong contextual message that equivalent work may already exist.

### Capability recommendations are not continuous

The platform matches solutions during discovery, but it does not consistently repeat that matching when the user:

- Adds a requirement.
- Clicks `+ Add step`.
- Describes a custom feature.
- Changes a workflow output.
- Saves an experiment.

Similarity checking should happen throughout the lifecycle.

### The capability tray is still primarily a component selector

It should become a **context-sensitive reuse assistant**:

> “You asked for safety-risk classification. Two existing capabilities may already do this.”

### Experiments are not sufficiently subordinate to a parent product

A new experiment should be stored as:

> Experimental branch of Work Order Intelligence

not as something that can gradually become an independent solution by default.

### IT sees duplication too late

The IT view currently emphasizes consolidation decisions and portfolio outcomes. It needs an earlier signal:

> “Four build attempts were redirected to existing capabilities before development began.”

### The Library does not yet distinguish solution families from every variation

Ordinary users should generally see:

- One preferred solution
- Approved configurations
- Supported optional capabilities

They should not see every experiment or branch as a separate catalogue entry.

# 3. Revised development priorities

## P0 — Required before Thursday

### 1. Add a reuse gate at every creation point

Run the same reuse check when a user:

- Describes a problem.
- Adds a requirement.
- Clicks `+ Add step`.
- Describes a new capability.
- Saves a workflow branch.
- Requests publication.

The reuse gate should return one of three recommended paths:

1. **Use existing**
2. **Improve existing**
3. **Create experimental alternative**

The system should recommend a path, not prohibit the user from proceeding.

### 2. Make `+ Add step` reuse-first

Current or intended behaviour:

> Click `+` → describe a new step → generate it.

Revised behaviour:

> Click `+` → describe the desired result → search existing capabilities → try an existing capability, improve it, or deliberately create a new experiment.

The interaction should remain extremely simple.

Example:

**What should happen here?**

> Flag maintenance issues that may create a safety risk.

The system responds:

> **A similar capability already exists**  
> Safety Signals identifies potential safety consequences in maintenance text.

Primary action:

**Try Safety Signals**

Secondary actions:

- See output example
- Improve this capability
- Create a different approach

The user should not need to search the Library manually before every customization. The Library search should occur automatically in context.

### 3. Add parent lineage and branch classification

Every modified workflow needs:

- Parent solution
- Parent version
- Exact workflow difference
- Experiment owner
- Configuration fingerprint
- Status
- Similarity cluster
- Promotion state

Visible UI language should be simple:

> Experimental improvement to Work Order Intelligence

not:

> New solution

### 4. Preserve the A/B workbench, but change its entry path

Version A should normally be the current certified solution.

Version B should normally start from:

- An existing reusable capability
- A modification of an existing capability
- A genuinely new experimental step only when needed

A/B execution should continue to use actual inputs and actual outputs.

### 5. Fix evidence integrity

The earlier source review identified evidence concerns that remain P0:

- Repeat votes should replace the user’s previous vote.
- Evidence must be tied to the exact Version B configuration.
- Changing Version B must invalidate or separate prior evidence.
- Owner and IT summaries must not combine results from different workflow revisions.
- Demo votes must remain visibly labelled.

Without this, proactive reuse may work, but the proof that an improvement is better remains questionable.

### 6. Change the save and publication actions

Avoid:

- Save as new solution
- Publish to Library

Use:

- Save experiment
- Continue testing
- Propose improvement to owner
- Propose as reusable capability
- Request new solution family

Creating a new solution family should be an exception requiring a reason, not a normal result of customization.

### 7. Close the consolidation loop

When an improvement is approved:

- Update the parent solution or create a governed successor version.
- Preserve the capability source.
- Update the Library.
- Mark relevant source products as folding, replaced, or retiring.
- Do not publish the experiment as another parallel solution.

## P1 — Valuable after the critical journey works

- Group similar experimental branches automatically.
- Show approved configurations beneath a solution family.
- Add output previews for approved configurations.
- Add a solution-intake flow that checks for existing solutions before a build begins.
- Add owner notifications when multiple teams request the same change.
- Add configurable thresholds for similarity and escalation.

## Deprioritize before Thursday

- Arbitrary AI-generated application development
- Complex workflow reordering
- Large IT portfolio dashboards
- Broad enterprise solution intake
- Numerous approved variants
- Sophisticated cost-allocation models
- Full application generation
- Automatic merging or retirement

# 4. Required UI and UX changes

The UI should prevent waste without becoming an obstacle.

Do not display constant duplicate warnings. Run matching quietly and interrupt only when a credible existing option is found.

## Discover

Keep:

- `Today`
- `Better`
- One recommended solution
- Up to two alternatives

Add a simple requirement coverage view.

Example:

| Requirement | Coverage |
|---|---|
| Detect recurring issues | Covered by Work Order Triage |
| Group similar failures | Covered by Pattern Finder |
| Flag safety consequences | Not currently covered |

A user can click an uncovered requirement to search capabilities immediately.

Do not show detailed scores unless the user selects `Why?`.

## Library and search

The Library becomes a first-class experience.

Default hierarchy:

**Business problem → Preferred solution → Approved configurations → Reusable capabilities**

Do not expose ordinary users to every experimental branch.

A solution card should show:

- One sentence describing the business outcome
- Supported status
- Primary owner
- What requirements it covers
- `Try with my input`

The most important new Library capability is not another filter. It is an **output preview**.

For approved configurations, show how outputs differ using the same sample input.

Example:

### Standard configuration

> Repeated vibration identified across four work orders.

### Safety-focused configuration

> Repeated vibration identified across four work orders. Potential bearing failure may create a safety consequence; supervisor review recommended.

Primary action:

**Try both with my input**

This lets the user understand functional differences without learning the underlying architecture.

## Workbench

The Workbench should always display the parent context:

> Improving Work Order Intelligence v2.1

Add a subtle status:

> Experimental branch — not a new production solution

### Revised `+` interaction

When the user clicks between workflow steps, open one compact drawer.

**What should the solution do next?**

The user types the requirement.

The system searches:

- Certified capabilities
- Approved configurations
- Existing experiments
- Similar proposed improvements

Then show no more than three options:

1. Best existing capability
2. Closest experimental improvement
3. Create a different approach

Do not show a full capability marketplace by default.

### Requirement addition

When a user adds a requirement during testing:

1. Add the requirement to `Better`.
2. Mark whether A already covers it.
3. Search the Library.
4. Offer the closest capability.
5. Add it to B only after confirmation.
6. Run the same inputs again.

This is a much better experience than automatically generating a new step.

## A/B testing

The main A/B screen should still show:

- Shared input
- Version A workflow
- Version B workflow
- Actual A output
- Actual B output
- Highlighted output difference
- User preference

Add provenance to changed output:

> Added by Safety Signals

Clicking it should identify:

- Source capability
- Source solution
- Responsible workflow step

This demonstrates why reuse is valuable.

After B is preferred, the action should be:

**Propose this improvement to Work Order Intelligence**

not:

**Publish Version B**

## Save behaviour

When the user saves an experiment, show:

> Saved as an experimental improvement to Work Order Intelligence.

Then, if similar work exists:

> Two other teams are testing a similar change.

Actions:

- Join existing experiment
- Compare approaches
- Continue separately

The platform should not reject the user’s work. It should give them the opportunity to combine effort before more time is spent.

## Solution owner

Do not show owners dozens of individual branches.

Group proposed changes by intent.

Example:

### Safety-risk classification

- 4 related experiments
- 3 teams
- 9 completed tests
- 68% preference for modified outputs
- 2 implementation approaches

Primary action:

**Review shared improvement**

The owner can decide:

- Adopt one existing approach
- Merge the strongest elements
- Request more evidence
- Keep as a local experiment
- Decline

## IT leader

Change the IT experience from a general catalogue review to an exception and health view.

The default page should answer:

1. Are users finding existing solutions before building?
2. Are repeated needs becoming shared capabilities?
3. Are experiments being incorporated into parent products?
4. Are supported production variants increasing or decreasing?

Recommended default metrics:

| Metric | Meaning |
|---|---|
| Reuse before build | Percentage of creation attempts redirected to an existing solution or capability |
| Existing capability acceptance | Percentage of suggested capabilities users actually tried |
| Improvements folded into parent products | Successful changes incorporated without creating a new solution |
| Production variants per solution family | Whether supported complexity is increasing |
| Duplicate effort found after development | A failure measure that should decline |
| Time to first useful test | Whether reuse is accelerating delivery |

Usage remains useful but should not determine governance by itself.

A low-use safety capability may still be highly important. A high-use feature may still be duplicative or poorly governed.

# 5. Deterministic reuse decision framework

The system needs a transparent, reproducible rule for deciding whether to recommend reuse, extension, or new experimentation.

## Reuse-fit score

Score each expressed need or proposed workflow step.

| Dimension | Weight |
|---|---:|
| Business problem and desired-outcome fit | 30 |
| Input and output compatibility | 20 |
| Workflow-position fit | 15 |
| User and operating-context fit | 10 |
| Data, control, and security compatibility | 15 |
| Maturity, support, and evidence | 10 |
| **Total** | **100** |

Hard exclusions:

- Required data is unavailable.
- Security or control requirements conflict.
- The capability cannot consume the required input.
- The capability cannot produce the required type of output.
- The component is deprecated or unsupported.

Recommended interpretation:

| Score | Recommended path |
|---:|---|
| 80–100 | Try the existing capability first |
| 60–79 | Start from and improve the existing capability |
| Below 60 | Permit a new experimental capability |
| Hard exclusion | Do not recommend reuse |

A user may still challenge a high-scoring existing capability. The system should ask only:

> What is missing from the existing approach?

That reason becomes part of the experiment, not a punitive approval request.

## Production-promotion gate

An experimental branch should not become a production variant merely because it exists.

For the hackathon demonstration, use a simple transparent gate:

- Tested against at least three representative inputs.
- No blocking control violation.
- Current Version B evidence only.
- Actual outputs reviewed.
- At least one recorded user evaluation.
- Named business owner.
- Named technical owner.
- Owner decision recorded.

The enterprise thresholds could later be configurable. The demo should make the principle visible.

## New-solution-family gate

A new solution family should only be considered when:

- The business problem is materially different.
- The user or operating context is materially different.
- The required input/output contract is materially different.
- A control or regulatory boundary requires separation.
- No existing parent can reasonably absorb the functionality.

Otherwise, the result should remain:

- An experiment
- A capability proposal
- A configuration
- An improvement to an existing product

# 6. Revised evaluation rubric

The earlier rubric over-weighted post-hoc consolidation. The revised rubric places proactive prevention first.

Maturity scale:

| Score | Meaning |
|---:|---|
| 0 | Absent |
| 1 | Concept only |
| 2 | Static or manually demonstrated |
| 3 | Functional on the seeded primary path |
| 4 | Governed, explainable, and reusable |
| 5 | Repeatable, measurable, and operationally closed-loop |

Based on the same source-level review, not a new runtime test:

| Criterion | Weight | Current maturity | Current points | Thursday target | Required proof |
|---|---:|---:|---:|---:|---|
| Proactive duplicate-effort prevention | 20 | 3.0 | 12.0 | 4.5 / 18.0 | Existing options appear before problem, requirement, or step creation effort begins |
| Explainable discovery and reuse | 15 | 4.0 | 12.0 | 4.5 / 13.5 | Ranked base and capability recommendations with visible reasons and hard constraints |
| Interactive A/B output evidence | 20 | 4.5 | 18.0 | 5.0 / 20.0 | Same-input execution, causal diff, current-revision evidence, user evaluation |
| Experiment lineage and anti-sprawl lifecycle | 15 | 2.0 | 6.0 | 4.0 / 12.0 | Experiments remain under parent solutions; similar branches are grouped; promotion is controlled |
| Many-to-one consolidation closure | 15 | 2.5 | 7.5 | 4.0 / 12.0 | Approved improvement updates the governed product and Library; redundant products receive dispositions |
| Simplicity and persona decision clarity | 10 | 3.5 | 7.0 | 4.5 / 9.0 | One decision per view, contextual reuse prompts, supporting detail hidden |
| Evidence integrity and demo reliability | 5 | 3.0 | 3.0 | 4.0 / 4.0 | Vote replacement, revision fingerprints, reset, fallback, smoke-tested critical path |
| **Total** | **100** |  | **65.5 ≈ 66** | **88.5 ≈ 89** |  |

The revised score is lower than the earlier 71 because the app is now being judged against a better interpretation of the problem:

> Not only can the platform consolidate work; can it prevent unnecessary duplicate effort from starting?

# 7. Revised Thursday acceptance test

The demo should prove the following sequence:

1. A user describes a maintenance problem.
2. The platform recommends an existing certified solution before any development begins.
3. The user adds a new safety-related requirement.
4. The platform finds an existing capability before generating anything new.
5. The user tries that capability against their own input.
6. Version A and Version B execute on the same records.
7. The resulting output difference is visible and attributable to that capability.
8. The user records which output is better.
9. The change is saved as an experimental improvement to the parent product.
10. The platform identifies any similar active experiments before further work occurs.
11. The owner reviews grouped evidence and approves the improvement.
12. The IT leader sees that the requirement was addressed without creating another production solution.
13. The Library now shows the improved governed product, not another separate app.

The revised competition story becomes:

> **Fusebox prevents duplicate work before it begins, proves improvements using actual outputs, and channels successful changes back into one governed product.**

That is more directly aligned with the Cenovus problem statement than a system that allows unconstrained creation and only identifies duplication afterward.
